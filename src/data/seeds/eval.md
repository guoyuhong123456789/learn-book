# RAG Evaluation Platform（RAG 评测平台）
---

## 一、项目介绍

### 1.0 项目介绍（面试口述稿）

> 口述原文（60 秒版）：
> 「这是我做的第二个项目，一个 **RAG 评测平台**，专门解决『RAG 答得好不好』这件事——把它从拍脑袋，变成**可量化、可回归、可定位**。
> 背景是：我们的 RAG 问答系统上线后，暴露了几个问题——**没有真实验证集**（靠人工攒问答，费人力、覆盖不全）；**判分靠人肉逐条打分**（跑一次全量要好几天）；**切分参数靠拍脑袋**（没法归因）；**坏例没有闭环**（知道答错了，但不知道错在哪、修没修好）。
> 所以我做了一套评测工程，把整条链路自动化：**测试集自动生成 → 批量评测 → 指标报告 → BadCase 闭环 → 发版回归**。
> 具体几块：测试集用 **Ragas 自动生成候选**，再人工筛选固化成**黄金集**（5 类问题 × 多类文档双维度覆盖）；评测用 **Ragas 四指标自动打分**，针对 Agent 还做了**按路由分层**的专属维度（路由准确率、库外拒答率这些，见问题 7）；**BadCase** 自动识别、人工审核打标签、修复后回归验证；另外做了**分块对比实验**，隔离变量去调切分参数，数据说话。
> 技术栈是 Vue2 + ElementUI 做前端、FastAPI + SQLAlchemy 做后端、Ragas 做评测、DeepSeek 当打分 LLM。架构上最大的特点是**两个仓库解耦**——评测平台只关心『怎么测』，被测服务通过一个评测契约（接口 + 数据结构）对接，平台不关心对方怎么实现。」


**三个亮点（面试官会顺着问，主动抛）**：
1. 两仓库解耦 + 评测契约——「工具与系统的边界用契约定义，不用实现耦合」（见问题 2）；
2. 按 route 分层评测 Agent——Ragas 四指标只评知识类分支，路由准确率/拒答率/工具效率单独聚合（见问题 7）；
3. BadCase 闭环 + 转正「复制而非移动」——数据生命周期设计（见问题 4、5）。


### 1.2 技术架构

```
┌──────────────────────────── RAG Evaluation Platform ────────────────────────────┐
│  Frontend (Vue2 + ElementUI + ECharts)                                          │
│   测试语料 │ 测试集管理 │ 批量评测任务 │ 报告可视化 │ BadCase 审核 │ 回归 │ 分块实验 │
│                                   │ REST /api                                  │
│  Backend (FastAPI + SQLAlchemy 2.0 + Pydantic v2)                               │
│   ├─ 测试语料     knowledge：上传切分 / 外部 MySQL chunk 直读（双语料源）        │
│   ├─ 测试集管理   testsets / versions / samples（版本管理 + 5 类覆盖校验）       │
│   ├─ 样本生成     Ragas TestsetGenerator（三语料源 + 分层抽样 + evolution_type）│
│   ├─ 批量评测     batch_runner：query（逐条）/ batch（整批）双模式 → Ragas 打分 │
│   ├─ 报告 / BadCase：四指标统计 · CSV 导出 · 题型差异化低分识别 · 审核 · 转正   │

│   ├─ 回归流水线   轮询 /api/health 版本变化 → 自动黄金集回归 + 指标 delta        │
│   └─ 分块对比实验 sweeps：多组切分 × 同测试集 → Recall@k/MRR（自包含语料/导出配置）│
└──────────────────────────────────────┬──────────────────────────────────────────┘
                                       │ POST /api/rag/query 或 /api/eval/batch
                        ┌──────────────▼──────────────┐
                        │  rag-main-service（被测方）  │  answer + retrieved_contexts
                        └─────────────────────────────┘
```



### 1.4 核心能力

- **测试语料**：上传 PDF/Markdown/txt 自动切分；或直读外部 MySQL chunk 表（免上传免重切分，天然与生产索引一致）；
- **测试集管理**：Ragas 候选生成（语料三选一 + 全量读取→分层随机抽样，抽样倍数可调）、黄金集 5 类问题×多类文档双维度覆盖校验、版本管理与固化；
- **批量评测**：两种调用模式对接被测服务（逐条 `/api/rag/query` / 整批 `/api/eval/batch`），Ragas 四指标自动打分，**按被测路由分层**（四指标只统计 knowledge 检索分支，chitchat/ambiguous/out_of_scope 分支由路由准确率/拒答率/工具效率等 Agent 维度衡量），报告可视化 + CSV 导出；
- **BadCase 闭环**：题型差异化自动识别（库外看拒答信号、模糊题放宽阈值）→ 人工审核打标签（幻觉/召回差/答非所问）→ 优化记录 → **转正沉淀进测试集**；
- **线上 badcase 回流**：连接被测服务生产库导入真实失败样本（source=production，可追溯），人工补全后固化——真实用户问法比合成题更有价值；
- **回归流水线**：主服务发版自动触发黄金集回归，输出新旧版本指标 delta 与通过率；
- **分块对比实验**：隔离变量（固定 embedding/top_k，只变切分）用同一黄金集测 Recall@k/MRR，按文档类型分组定参，一键导出生产切分配置建议、一键用最优参数建评测任务。

## 二、作业流程

### 2.1 黄金集从 0 到 1（测试集建设）

```
① 测试语料    上传业务文档（切分参数须与生产一致）或直读外部 MySQL chunk 表
② 候选生成    Ragas TestsetGenerator 批量生成：先读全量 → 分层随机抽样（按文件格式保证覆盖）
              → 每条自带 question / context / ground_truth，自动记录 evolution_type
              （simple 单chunk事实 / reasoning 推理计算 / multi_context 跨文档综合）
③ 人工筛选    4 件事：剔除书面化问题 / 核对修正 ground_truth / 确认 context 支撑 / 标注问题类型
④ 覆盖校验    5 类问题是否齐全（fact / reasoning / vague / out_of_kb / edge），缺失自动提示
⑤ 固化黄金集  达标后冻结为稳定版本，供批量评测与回归使用
```

**黄金集 5 类问题（面试重点）**：简单事实查询 / 多段文档综合推理 / 模糊提问（信息不全，测澄清）/ **知识库不存在的问题（测拒答、防幻觉，必加）** / 易混淆边界问题。

### 2.2 评测 → BadCase → 修复 → 回归 闭环（含线上 badcase 回流与转正）

```
线上 badcase（被测服务生产库，真实用户反馈）
   │  probe 探测列 → import（只导入未修复，按 question 去重）
   ▼
候选样本（source=production，source_ref 记录 库/表/行 可追溯）
   │  人工筛选：补 ground_truth、标题型、剔除误报 → 固化
   ▼
黄金集版本 → 批量评测任务（query / batch 模式）→ Ragas 四指标打分
   │  题型 + 路由双维度识别低分（库外看拒答信号 / 模糊题放宽阈值 / 常规题看分数；非检索分支低分不标，误路由必标）
   ▼
候选 BadCase → 人工审核：打标签（幻觉/召回差/答非所问）+ 优化记录
   │  修复被测服务（补文档 / 调检索 / 改 prompt）
   ▼
重跑评测验证 → 连续通过 + 人工确认
   ▼
转正：复制为测试集样本（继承题型/答案，source_ref 记 badcase_id），badcase 标记 converted
   │  回归流水线：主服务发版 → 自动跑黄金集 → 新旧指标 delta
   ▼
新版本发布，坏例不再复发（防回归）
```

**闭环的关键设计**：转正是**复制而非移动**——坏例固化进测试集后，badcase 记录保留可回溯；同版本内按 question 判重，防止反复转正堆积重复样本。

### 2.3 分块实验流程（调参闭环）

```
选语料（复用测试语料 或 实验自包含上传） + 选黄金集版本 + 多组切分参数（如 300/30、500/50、800/80）
   → 平台内独立检索（不依赖被测服务，纯检索层）→ Recall@k / MRR（可按文档类型分组）
   → 导出生产切分配置建议 JSON（整体最优 + 各类型最优）
   → 一键用最优参数建批量评测任务（端到端验收）
```

调参思路：**分块实验筛参数（快、便宜、灵敏），批量评测验收效果（贵、贴近真实）**——两步都跑，数据说话。

## 三、开发中遇到的问题与做法（面试素材）

### 问题 1：库外拒答、模糊提问被自动误标为 BadCase

**现象**：黄金集里一条 out_of_kb（库外拒答）和一条 vague（模糊提问）总是落到候选 badcase——即使被测服务回答得完全正确（正确拒答 / 正确澄清反问）。

**根因**：自动 badcase 判定是纯分数规则 `avg_score < threshold`，代码不感知样本题型；而 **Ragas 四指标是为"标准库内问答"设计的**——正确拒答的句子命中不了任何检索片段（context_recall≈0），正确澄清反问话术与期望答案不匹配（faithfulness/answer_relevancy 低），天然给低分。**反向坑**：库外题如果被测硬答（幻觉），分数反而可能高于拒答，纯分数规则连真问题都会漏掉。

**做法：按题型差异化判定**（`auto_mark_badcases` 按 `question_type` 分流）：

| 题型 | 判定逻辑 | 效果 |
|---|---|---|
| out_of_kb | 不看分数，看**拒答信号**（空回答或含"未找到/无法回答/知识库中未…"）：正确拒答→不标；硬答→**必标**（note 标注疑似幻觉） | 正确拒答不误杀；幻觉硬答必抓（哪怕高分） |
| vague | 阈值放宽到 min(全局阈值, 0.35) | 澄清/尽力答不误杀，过低分数仍标 |
| fact / reasoning / edge | 维持原判 avg_score < threshold | 行为不变 |

**面试话术**：自动 badcase 识别不能只按分数一刀切，先要问"这个指标对这类行为是不是有效的度量"。Ragas 四指标对拒答、澄清天然失真——先保证 badcase 入口的语义正确，后面的修复、回归闭环才有意义；否则每天在审核"假坏例"，真问题反而被高分掩盖。

### 问题 2：被测 RAG 地址填了却打不到（契约不匹配）

**现象**：批量评测任务里被测地址填 `http://localhost:8000/api/eval/batch`，任务一跑全部 404。

**排查与根因**（三层）：
1. 代码把填的地址当 base URL，硬拼接了 `/api/rag/query`——实际请求变成了 `/api/eval/batch/api/rag/query`；
2. 更深一层：**被测服务根本没有 `/api/rag/query`**——它是 LangGraph 路由式 RAG Agent（v1.0.0），只提供批量评测接口 `/api/eval/batch`（接收 `{questions, ground_truths, module}` 返回逐条结果），**两边的契约从一开始就不匹配**；
3. 附带问题：默认地址指向 8001，而 8001 上跑的其实是评测平台自己（mock 模式）——地址、端口、服务实例三个概念串了。

**做法：调用模式显式化 + 契约探测**（`call_mode` 二选一）：

| 模式 | 语义 | 地址填写 | 适配服务 |
|---|---|---|---|
| query（逐条） | 逐条 POST `{base}/api/rag/query` | base 地址 | 传统 RAG，返回 answer + retrieved_contexts |
| batch（整批） | 整批 POST 完整 URL，按响应 index 对齐样本 | **完整接口地址** | Agent/全链路服务，已有批量评测接口 |

批量模式额外做了版本自动探测（从 URL 反推 base 调 `/health` 拿 service_version）、失败样本落库可见。

**面试话术**：评测工具对接被测系统，最容易踩的坑是**想当然地假设对方有某个接口**。做法是先摸清"被测侧有什么契约"（看 OpenAPI），再让调用模式显式可配置，而不是写死一种。**工具与系统的边界，应该用契约而不是地址来定义。**

### 问题 3：已完成任务不能重跑（重跑语义设计）

**现象**：任务跑完发现被测服务升级了，想重跑，按钮是灰的——前端 disabled 只放行 failed/pending，后端对 done 直接 400。

**根因**：最初把"重跑"设计成"失败重试"，没考虑"被测升级后重新评测"这个更常见的场景。

**做法**：重跑放开为**任何非 running 状态**；语义定义为"**清空旧结果与旧 badcase → 用原配置重新评测**"（先删 Badcase 再删 EvalResult，避免 SQLite 悬空引用），报告页与 badcase 审核页只面对新一批数据；running 中禁止并发。

**面试话术**：功能按钮的可用性本质是**状态机的转移规则**。把"重跑"从"失败重试"扩展成"以新配置重新评测"，要先想清楚旧数据的处置（清空还是保留），否则重跑几次报告页就乱了。**状态迁移时，数据一致性问题比按钮灰不灰重要得多。**

### 问题 4：线上 badcase 不能直接塞进平台 badcase 表（数据模型边界）

**现象**：想从被测服务生产库导入线上 badcase，最初想直接 INSERT 进平台 badcases 表。

**根因**：平台 `Badcase` 表强绑定 `result_id`（外键到 eval_results，NOT NULL）+ `task_id` + `sample_id`——它是"**某次评测答卷**"的标记；线上 badcase 只有 question/answer/反馈，没有评测答卷，硬塞破坏外键约束，且**语义混了**：线上 badcase 是"真实用户反馈"（种子上游），平台 badcase 是"指标低分"（验证下游）。

**做法：导入为候选样本**（source=production，source_ref 记录库/表/行主键可追溯），走"导入 → 人工筛选补全 → 固化 → 评测 → 平台 badcase"通道；复用外部 MySQL 直读骨架（probe 探测列 + 只导入未修复 + 按 question 去重）。

**面试话术**：导入外部数据前先问"它属于哪一层"。平台 badcase 表有外键约束，线上记录没有评测结果，硬塞会破坏模型——所以走候选样本通道，让数据在正确的生命周期里流转。**数据模型边界的判断，比功能实现本身更重要。**

### 问题 5：BadCase 转正的判重与可回溯设计

**设计问题**：转正（badcase → 测试集样本）时，选择"复制"还是"移动"？转正到哪个版本？

**做法**：
- **复制而非移动**：从 badcase 关联的原始样本继承 question/答案/上下文/题型，写入目标版本（source=badcase，source_ref 记 badcase_id/task_id）；badcase 记录保留并置 converted——坏例下次再犯可回溯，避免"移动"导致历史丢失；
- **按 question 在目标版本内判重**：原样本已在目标版本 → 跳过（防止反复转正堆积重复样本）；这也意味着**转正的正确场景是"跨版本沉淀"**（坏例来自开发集 → 固化进黄金集）；
- 转正后样本带题型与来源标签，可进覆盖校验，不影响黄金集 5 类统计。

**面试话术**：转正是"题目"的再沉淀，不是"记录"的迁移。复制 + 判重 + 可追溯，让坏例既能防回归、又不污染测试集；同时想清楚转正的语义边界（跨版本有效，同版本天然重复）。

### 问题 6：评测指标都低，怎么排查——是测试集的问题还是 RAG Agent 系统的问题？

**现象**：跑完批量评测，faithfulness / answer_relevancy / context_precision / context_recall 四项指标都偏低，不知道是黄金测试集质量不行，还是整个 RAG Agent 项目（检索/排序/生成）有问题。

**核心思路：先归因，不急着改系统。** 指标低 ≠ 系统差，按"第 0 层验尺子 → 第 1 层指标组合定位 → 第 2 层决定性实验 → 第 3 层对照组"逐层排查。

**第 0 层：先验证测试集是不是合格的尺子（最便宜，先做）**

| 检查项 | 怎么查 | 判断 |
|---|---|---|
| ground_truth 与知识库一致吗 | 抽查 5-10 条对照原文 | 不一致 → 分数失真，先修正再谈系统 |
| 标准上下文支撑答案吗 | 同上 | context 不支撑 → recall/precision 虚低 |
| 题型分布合理吗 | 平台覆盖统计 | vague / out_of_kb 占比高 → 指标天然低，**这不是系统错** |
| 切分参数与生产一致吗 | 测试语料 chunk_size/overlap | 不一致 → 测试集分布错位，评测失真 |
| 有没有"不可能答对"的题 | 过滤库外题单独看 | out_of_kb 类本来就不该有高 recall |

**第 1 层：用指标组合定位链路层级**（四指标不是平均用力，各自对应链路不同环节）：

| 指标组合 | 定位 | 排查方向 |
|---|---|---|
| context_recall 低（precision 正常） | 检索**召回**不足 | 知识没进库 / 切分策略 / embedding 质量 |
| context_precision 低（recall 正常） | 检索**排序**差 | top_k 太小 / 精排模型 / 混合检索权重 |
| recall/precision 高，faithfulness 低 | **生成**幻觉 | prompt 约束 / LLM 能力 / 上下文被截断 |
| 前三项高，answer_relevancy 低 | **生成**答非所问 | prompt 指令不明确 / 多轮信息丢失 |
| **四项全低** | 系统性或尺子问题 | 被测服务没起来 / 契约不匹配 / 回到第 0 层 |

**第 2 层：两个决定性实验（平台现成能力）**

1. **分块实验单独测检索层**（不经过生成）：同一黄金集跑 Recall@k / MRR。检索层分高 → 问题在生成层（查 prompt/LLM）；检索层也低 → 查切分/embedding/top_k；
2. **抽样看 badcase 的 contexts**（最快的一刀）：报告里看低分样本"被测检索到的 contexts 里有没有标准答案"——**有答案没答对 → 生成层问题；没答案 → 检索层问题**。看 10 条即可定性。

**第 3 层：对照组归因**——同测试集，一次只动一个变量（切分 / embedding / prompt / LLM），指标跟着谁变，谁就是根因。

**记忆口诀**：recall 低=知识没捞到（检索）；precision 低=捞到了排后面（排序）；faithfulness 低=编造（生成）；relevancy 低=答非所问（生成）。**先问"尺子歪没歪"，再问"捞到没捞到"，最后问"答对没答对"。**

**面试话术**：指标低我不会先改系统，而是先归因。第一步验证测试集本身是不是合格尺子——ground_truth 是否对照原文、题型分布是否合理（vague 和库外题天然低分，不是系统问题）、切分参数是否与生产一致。第二步用指标组合定位链路：context_recall 低是检索召回问题（查切分/embedding/入库），context_precision 低是排序问题（查 top_k/精排），faithfulness 低是生成幻觉，answer_relevancy 低是答非所问。第三步做决定性实验：用分块实验单独测检索层 Recall@k，如果检索没问题那就是生成层；再看 badcase 的 contexts——检索结果里有没有标准答案，有答案没答对是生成问题，没答案是检索问题。最后做对照组，一次只动一个变量，指标跟着谁变谁就是根因。这套排查框架本身，也是评测平台"可定位"价值的体现——低分不再是一个数字，而是一条可追踪的链路。

### 问题 7：测 RAG Agent 不能直接用 RAG 四件套（按 route 分层）

**现象**：被测服务是 LangGraph 路由式 RAG Agent（chitchat / ambiguous / out_of_scope / knowledge 四路由），平台却对**所有样本统一跑 Ragas 四指标**——结果正当拒答、正当澄清反问被标成低分 badcase，报告的指标均值也失真。

**根因**：Ragas 四指标（faithfulness / answer_relevancy / context_precision / context_recall）是为**"单轮检索-生成"的经典 RAG**设计的，隐含假设是"答案由检索上下文生成"。Agent 的行为超出了这个假设：

| 指标 | 经典 RAG 假设 | Agent 场景下的失真 |
|---|---|---|
| faithfulness 忠实度 | 答案 claims 应能被检索 context 支撑 | Agent 回答来源多样：chitchat/ambiguous 分支**不检索**；sql_query 查出的结构化数据不在检索片段里；"[片段N]"引用标记/元信息被拆成 claims 校验失败 → 正当回答被判幻觉 |
| answer_relevancy 答案相关性 | 答案应正面回答问题 | 澄清反问（ambiguous 正确行为）、说明"不在知识库范围"（out_of_scope 正当拒答）被判"与问题不直接相关"→ 做对了反而扣分 |
| context_precision 精确率 | 每个检索片段与问题相关 | Agent 多轮检索后 references 是多次检索的并集，混入与最终答案无关的片段 → 精确率被稀释 |
| context_recall 召回率 | context 覆盖 ground_truth | 相对可用（评检索质量），但测不了 Agent 的决策与拒答 |

**做法：按 route 分层 + Agent 专属维度**（被测批量接口本就返回 route / route_reason / tool_calls / steps，改造前这些信号被白白浪费）：

1. **四指标只对 route=knowledge 分支计算**（真实检索-生成的部分，四指标依然有效）；chitchat / ambiguous / out_of_scope 分支不打四指标（scores 置空，avg_score 为 None，不参与指标均值与低分判定）；
2. **Agent 专属维度单独聚合**（`report.py` 新增 `agent_metrics`，与四指标正交）：
   - **路由准确率**：按黄金集题型推期望路由（fact/reasoning/edge→knowledge；vague→ambiguous 或 knowledge；out_of_kb→out_of_scope 或 knowledge+拒答），逐条判 route 是否合理；
   - **库外拒答率 / 硬答数 / 库内误拒数**：拒答行为是否正确；
   - **平均 ReAct 步数 / 平均工具调用数**：效率与成本（多步=高 token 成本）；
   - **引用标注率**：knowledge 分支回答是否带 [片段N]（生产合规要求）；
3. **badcase 判定同步分层**：非检索分支的低分不再标 badcase（正当拒答/澄清不误杀）；**库内问题被误路由**到 chitchat/ambiguous/out_of_scope（误拒、答非所问）反而必标；out_of_kb 硬答必标；
4. 旧数据兼容：route 为空（历史任务/query 模式）按全量统计，报告不破。

**实测效果**：同一任务（员工手册黄金集 30 条），改造前报告把 **4 条库外正确拒答**（avg 0~0.23，Ragas 对拒答天然给低分）误列为候选 badcase；改造后 low_score 降为 0，同时新增可解释的 Agent 维度（路由准确率 / 拒答率 100% / 引用标注率 96.7%）。**正当行为不再被"尺子不准"冤枉，真正的问题（误路由、硬答幻觉）反而更容易暴露。**

**面试话术**：评测 Agent 之前先问"这套指标的设计假设是什么"。Ragas 四指标假设"答案由检索上下文生成"，而 Agent 有路由决策、工具调用、拒答行为——直接套用会把正当拒答判成低分、把工具查询结果判成幻觉。我的做法是**按 route 分层**：四指标只评真实检索分支，路由准确率/拒答率/工具效率等 Agent 专属维度单独聚合，badcase 判定同步分层（正当拒答不误杀、误路由必标）。核心思想是"**先确认指标对这类行为是不是有效的度量，再谈打分**"——这和问题 1（题型差异化 badcase 判定）一脉相承，只是从"题型"维度升级到"行为（route）"维度。
