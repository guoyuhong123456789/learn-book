## 第一轮：开场自述

### Q1. 简单介绍一下这个项目，你负责哪部分，最有挑战的是什么？

**参考答（30~60 秒版）**：

> 口述原文：
> 「这个项目得先说背景。用户有大量的管理制度、流程文件、会议纪要，另外业务数据散在台账和数据库里。用户以前想查个制度，得自己翻文档；想要个统计，得找人写 SQL。效率很低，而且不同人查出来的口径还经常对不上。所以就想着做一个统一的入口，制度也能问、数据也能问。
### 0.3 系统整体介绍（60 秒口述）

> 口述原文：
> 「我做的是这么一套东西：用户用自然语言提问，系统去检索单位内部的制度文档，然后生成一个带引用的答案。
> 底层是拿 LangGraph 的 Plan-and-Execute 搭的，我大概分四块说。
> 第一块是**检索**。用户的问题进来先进行路由，对于知识类先做 Query 改写，然后两路召回——一路是向量的，用 M3E 抓语义；一路是 BM25，抓关键词。两路用 RRF 融合，再用 bge-reranker 精排，最后取 Top4。
> 第二块是**Agent 这条线**。前面有个路由，先把问题分成闲聊、模糊、库外、知识四类，只有知识类才进主链路。进去之后 Planner 一次性把步骤规划好，execute 并行跑几类 worker——向量检索、只读 SQL、文档生成、数值计算、还有答案生成，最后有个评审节点把关，主要干两件事：一是查幻觉，二是打相关性分。
> 第三块是**工程化**，就是保证它真能用。答案走流式，首字 500 毫秒以内，思考过程也是实时推的，前端从原来黑盒等着变成像打印机一样一行行往外蹦。会话记忆用 LangGraph 的 Checkpoint 存。
> 第四块是用 Redis 做了三件事：一是检索的 KV 缓存，同一个 query 命中就直接跳过 embedding、向量库和 rerank；二是会话上下文放 Redis，服务就是无状态的，多实例能共享；三是滑动窗口限流，保护后面的 LLM 和向量库。
> 效果我分几块说。**性能上**，问答 P50 从 3.7 到 5.5 秒压到了 2 秒以内——预热加检索缓存命中的前提下；首字 500 毫秒以内，体感就是秒回、边出边看。**检索质量上**，离线评测集 100 条，Hit@1 是 90%、Hit@3 是 100%，跑三轮结果一致。**可信上**，答案是带引用的，评审节点还做幻觉检测和相关性打分。**可迭代上**，全链路 trace 都落库，接评测平台做 BadCase 闭环，上线后能持续优化。」

## 你的切分策略是什么？
### Q34. 你这个 RAG Agent 的切分策略怎么设计的？效果怎么样？

**参考答**：

> 核心是「**按块类型分派**，不搞一刀切」。先把文档解析成不同类型的块，每类用对应的切分策略。整个切分只有一个入口 `create_text_splitter`，返回自研的 `TableAwareTextSplitter`，对外兼容 `RecursiveCharacterTextSplitter` 的接口，随时能无感替换。
>
> 具体分四类：
> - **表格块**：表格是 RAG 里最容易切坏的——按标点、长度递归切，表头和数据行被劈到不同切片，召回只剩数字、丢列含义。所以**整表优先**，放不下（超 `TABLE_CHUNK_SIZE=400`）才按行切，**每片重复表头**，单行再长也不硬切。解析层 PDF 用 pdfplumber、Word 用 python-docx、Excel 用 openpyxl、CSV/纯文本用启发式，**统一转 Markdown 表格**再进切分器。
> - **普通正文**：递归字符切分，`CHUNK_SIZE=300` / `CHUNK_OVERLAP=50`，分隔符 `\n\n、\n、。、，`，末尾空串兜底——保证 chunk_size 是硬上限。
> - **OCR 文本**：影印版没有自然段落、残留空格误识别符号，换更细的分隔符（加全角标点、英文空格、空串）。
> - **制度法规**：条款级切分，一条一块，超长二次切分补条款前缀——条款是文档自带的权威语义边界。
>
> 效果上我诚实说：**切分策略本身没有单独的「切片质量」指标**，它的效果间接体现在端到端检索——检索评测集 100 条，Hit@1 90%、Hit@3 100%。切分参数的取值不是拍脑袋，配合评测平台的**分块对比实验**（固定 embedding/top_k、只变切分，测 Recall@k/MRR）隔离变量验证。
>

⚠️ **两个诚实的坑（面试官可能追）**：
1. **切分策略没有独立效果指标**——被问「怎么证明 300/50 是好的」，答「靠分块实验隔离变量测 Recall@k/MRR」，别硬编数字；


## 第二轮：编排模式（Agent 岗必挖）

> **先记这张节点图（7 个主节点）**，后面所有编排相关的问题都围绕它展开：
>
> | 节点 | 职责 |
> |---|---|
> | router | 前置路由：规则快通道 + LLM 四分类 |
> | planner | 一次规划多步，输出 steps |
> | execute | 并行执行 worker（retrieval / sql / doc / calc ） |
> | assess | 确定性评估条件边：判断素材够不够 |
> | answer_worker | 生成候选答案 draft_answer |
> | review_worker | 校验把关：幻觉检测 + 相关性打分 |
> | finalize | 出最终答案 → trace 落库 → 返回 |
>
> 流转主线：`router → planner → execute → assess → answer_worker → review_worker → finalize`。两个回环（assess 素材不足回 planner、review fail 回 planner）都限轮次防死循环。

### 前置裁决 + 后置纠偏是怎么做的？
**后置纠偏（Planner 输出之后，规则分流）： Planner 给完 steps 后，不直接执行，先看它是不是空：**

> plan_steps 非空 → 才进 execute 执行；
> plan_steps 空（说明状态已确定、没什么好规划的了）→ 直接走 review/finalize，跳过执行。
> 这就是「纠偏」——LLM 输出「空规划」时，用确定性规则把它导向收尾，而不是傻傻执行一轮空步骤。

**前置裁决（回 Planner 之前，规则先拦一道）： execute 执行完，进 assess 条件边，用确定性规则看「这一轮到底拿到素材没有」：**

>素材不足 → 回 planner 重规划，但**「最多 1 次」补证据**（这个上限就是前置裁决的拦断，防无限重规划）；
>已有候选/文档 → 直接走 review，不再回 planner；
>素材足 → 直接走 answer，不再回 planner。
>所以「前置裁决」的本质是：在决定「要不要再调 Planner」之前，先用 assess 的规则裁决掉大部分情况——只有「素材不足」才放行回 Planner，其余情况都确定性短路，省掉 Planner 的 LLM 调用。

**一句话总结**
>后置纠偏 = Planner 输出后用 plan_steps 空/非空 分流；前置裁决 = execute 后用 assess 条件边判断素材，只有「素材不足」才回 Planner（且限 1 次），其余确定性短路。 都是纯规则、不调 LLM，靠这些条件边把「不可靠的 Planner」包起来。

### Q3.Planner规划的内容是什么？ 一次最多规划几步？规划错了怎么办？max_rounds=10 是防谁的？
**Planner 管「取素材的决策」（retrieval/sql/doc/calc），answer/review/finalize 是固定的确定性收尾链，不由 Planner 规划。**

**参考答**：

> Planner 一次输出一组 steps，比如 `["retrieval","sql","doc","calc"...]`，前面还有确定性裁决做前置、后置纠偏。如果规划有问题——比如素材没拿到、或者评审 fail——会回到 planner 重规划，但**有轮次上限**。`MAX_PLANNER_ROUNDS=10` 防的就是**重规划死循环**：防止 planner 反复规划、执行、再规划，把请求拖死。

⚠️ **需你确认**：文档没有明确写「Planner 单次 steps 最多几步」。被问到「最多几步」时，如果你没有硬限制，就如实说「没有硬性上限，由 Prompt 约束输出，靠后面的 assess 做纠偏」。

### Q4. execute 里哪些 worker 之间真的没有依赖？Planner 把 doc 排在 retrieval 前面会怎样？

**参考答**：

> 真正**没有依赖**的是 retrieval、calc， sql——它们各自独立执行、互不消费对方结果，所以放在并行批里用 ThreadPoolExecutor 跑。**有依赖的是 doc**：文档生成必须读到检索片段、SQL 结果和计算结果，所以它放在主线程串行批。
>
> 如果 Planner 把 doc 排在 retrieval 前面，doc 拿不到素材，assess 会判定「素材不足」，回 planner 重规划——所以即便规划顺序不合理，也有兜底，不会直接出错。

💡 **口径**：核心一句是「**并行无依赖 + 串行有依赖 + 共享 state，worker 之间零参数耦合**」。

### answer_workerne内部如何做的？
answer_worker 内部就是「拿素材 → 拼 prompt → 调 LLM 生成候选答案」三步。综合文档里几处线索，具体是这样：

answer_worker 内部怎么做
第 1 步：从 state 读素材

它不自己取素材，而是读前面 execute 已经写进共享 state 的结果（§11.2 里写了「answer_worker 从 state 读素材」）：

references（检索到的片段）
sql_result（SQL 查询结果）
calc_result（计算结果）
doc_result（生成的文档）
第 2 步：拼 prompt

用 prompts.py 里的「回答」提示词（目录结构里明确有「路由 / Planner / 回答 / 校验评审 / …」），把用户问题 + 上面这些素材拼成一个生成 prompt。

第 3 步：调 LLM 流式生成

调 LLM（trace 里 caller="answer_agent"）；
流式生成：用 get_stream_writer() 把「引用」和「逐 token 的增量」推出去（§6.3 里写了「流式那个 answer 节点用 get_stream_writer() 推引用和逐 token 增量」）；
生成的答案写入 state，就是 draft_answer（候选答案）。

## 第三轮：检索（追细节，验证真做过）
***用户的问题进来先进行路由，对于知识类先做 Query 改写，其余类别跳过检索。***
### 你是如何对问题进行路由的？
>路由是整条链路最前面的一步，负责把用户的问题分成四类——闲聊、模糊、库外、知识，只有「知识类」才进主链路去查库、走后面那一套。我是分两层做的：

>第一层是规则快通道，零成本。先用正则匹配纯问候语（比如「你好」「在吗」）直接判成闲聊；再命中知识库、文档生成、数值计算这些关键词的直接判成知识类。这一层能拦掉一大半明显的，省掉一次 LLM 调用。

>第二层才是 LLM 四分类。规则判不出来的，交给 LLM 输出一个 JSON，四选一。这里有两个关键设计：一是优先级排序（闲聊 → 模糊 → 知识 → 库外），二是兜底原则——拿不准一律判知识类，宁可多查一次库，也不漏答。

>为什么这么偏？这是个代价不对称的设计：把该答的问题误判成库外拒答，代价很高；把库外的问题误判成知识类、多查一次，代价很低。所以整个路由我是刻意往「知识类」偏的，路由 LLM 万一失败也默认走知识类。

>这里我踩过一个真实的坑：初版 prompt 把 out_of_scope 定义成「与知识库领域（管理规定、制度流程）明显无关」，结果「报销流程怎么走」「发票丢了还能报销吗」这种业务边缘问题全被误判成库外拒答了。原因是领域锚定太窄、「明显无关」约束太弱、又没给示例。后来改了四处——分支按优先级排、放宽 knowledge 定义、收紧 out_of_scope、补了 7 条 few-shot（示例），再用 20~30 条路由测试集对比验证，同时监控线上 out_of_scope 占比，超过 15% 就是误伤信号。

### Q10. Query 改写怎么做的？每个问题都要改吗？有什么代价？改写中大模型是如何把口语 / 指代问题改写成完整检索问法？

**参考答**：

> **怎么做的**：Query 改写是检索前的一道预处理，放在 `vector_search` 工具里。我做的**不是无脑改，而是「有条件改写」——规则快通道先判断**：含指代词（它 / 这个 / 上述）或信息不全（过短 / 无实体）→ **必改**；问题已完整（长度够、含专有名词、无指代）→ **直接跳过改写**，省一次 LLM 调用。需要改写的才调 LLM（temperature=0，保证稳定），把口语 / 指代问题改写成完整检索问法，比如「它怎么算的」→「XX 补贴金额的计算方式」。有兜底：失败或返回空就退原 query。埋点在 `llm_calls` 里 `caller="query_rewrite"`。
>
> **是不是每个都改**：不是，分两层。第一层，前置路由先分四类，只有「知识类」才进检索——闲聊 / 库外 / 模糊在路由就分流了，根本不触发检索、也不改写。第二层，进检索的**也不是都改**，靠上面的规则快通道：完整清楚的问题直接跳过，只有口语化、带指代、信息不全的才走 LLM 改写。
>
> **代价**：只有被规则判定「要改」的问题才多一次 LLM 调用；规则跳过的那些零额外开销。温度设 0 是为了稳定。

> **如何改写**：大模型没记忆，但 Query 改写时我们把「历史对话」从 Redis 捞出来、拼进 prompt，让模型靠「看到上文」来消解「它/那个」这类指代，再改写成完整问法。 记忆在 Redis，不在模型里。

⚠️ **一个诚实点**：文档没有「改写质量」的独立指标——被问「怎么知道改写得好不好」，答「目前是通过端到端检索命中率间接看的」。

### Q37. 你的混合检索具体是怎么做的？

> 检索最基础的问题，先讲完整流程，面试官会再从某个环节往下追（就接到 Q7~Q10）。

**参考答**：

> 我的混合检索是「**Query 改写 → 双路召回 → RRF 融合 → 精排**」四步。
>
> **第一步，Query 改写**（有条件，见 Q10）：口语化、带指代的问题先改写成完整问法。
>
> **第二步，双路召回**：一路是**向量语义召回**，用 M3E 把 query 和 chunk 各自编码成向量， 召回 Top 20，抓的是语义近义；另一路是 **BM25 关键词召回**，用 jieba 分词 + `rank_bm25.BM25Okapi` 对 MySQL 全部分片建索引，对关键词、条款号、专有名词这种精确匹配。
>
> **第三步，RRF 融合**：两路分数没法直接比（向量给的是 distance、越小越近，BM25 给的是相关性分、越大越相关，量纲不同），所以用 RRF 只按排名融合，`score = Σ 1/(k + rank)`、k 固定 60，融合后取 Top 20。
>
> **第四步，精排**：把融合后的 Top 20 交给 bge-reranker（Cross-Encoder）精排，最终取 **Top 4** 喂给 LLM。**混合检索只负责「该进的候选先进来」，最终顺序由精排统一纠偏。**

向量路召回 20 条 ─┐
                  ├─ RRF 融合 → 取 Top 20 → bge-reranker 精排 → 取 Top 4
BM25 路召回 20 条 ─┘

### 双路召回的语义召回是如何做的？
> 语义召回就是向量那一路，核心思路是「把文本变成向量，靠向量距离来判断语义近不近」。分两个阶段：

> 离线入库的时候，文档切好的每个 chunk，都用 M3E 编码成一个 768 维向量。

> 在线检索的时候，用户的问题先做 Query 改写，然后把改写后的 query 也用 同一个 M3E 编码成 768 维向量，在向量库里做相似度检索（ANN 近似最近邻），召回 Top 20 个最相似的 chunk。
### 双路召回的BM25关键词召回是如何做的？知识库更新了如何做？

> BM25 是**关键词那一路**，做的是**词级别的精确匹配**，分三步：
>
> **第一步，分词**：中文没有空格分隔，先用 **jieba** 把知识库里的每个 chunk、以及用户的问题，都切成一个个词。
>
> **第二步，建索引**：对知识库全部分片，用 **`rank_bm25.BM25Okapi`** 建一个**进程内缓存索引**——本质是统计每个词的词频（TF）和逆文档频率（IDF），也就是「某个词在哪些 chunk 里出现过、出现多少次、它多不常见」。
>
> **第三步，打分召回**：用户的问题分词后，用 **BM25 算法**给每个 chunk 打分——它本质是 TF-IDF 的改进版：query 里的词如果和 chunk 里的词**精确匹配**，就按词频和稀有度加分。所以像**条款号、专有名词、数字**这种精确词，只要在 chunk 里原样出现，就能稳稳命中，最后按分数排序召回 Top 20。

> 知识库更新了如何做？上传文档切分、chunk 写入 MySQL 成功后，紧接着从 MySQL 全量读一遍重建索引；删除文档 / chunk 也走同样的触发。
> 为何不用增量更新？规模小用全量重建（简单、几秒、不会错），规模大了才值得做增量——因为 BM25 的 IDF 和平均长度是全局统计，增量要处理『牵一发动全身』的问题。

### BM25 索引内容是啥？（索引里存的是什么）

> BM25 索引的内容是一套「**倒排索引 + 统计量**」，核心就是「**每个词在哪些 chunk 出现过、出现几次、它有多稀有**」。具体存四样：
>
> 1. **语料**：每个 chunk 被 jieba 分词后的词序列；
> 2. **词频（TF）**：每个词在每个 chunk 里出现几次；
> 3. **文档频率（DF）→ 逆文档频率（IDF）**：一个词在多少个 chunk 里出现过，越稀有 IDF 越高、区分度越强；
> 4. **文档长度 + 平均长度**：每个 chunk 多少词，用于 BM25 的长度归一化。
>
> 对应 `rank_bm25.BM25Okapi` 内部，大致就是 `corpus_size`（文档总数）、`avgdl`（平均长度）、`doc_freqs`（每个文档的词频表）、`idf`（词 → IDF 值）、`doc_len`（每个文档长度）这几个结构。

**举个例**：

> 假设知识库 3 个 chunk：`报销流程需要提交发票` / `发票丢失如何处理` / `差旅报销标准`。
>
> 分词后索引里存的是——**词频**：「发票」在 chunk1、chunk2 各 1 次、chunk3 0 次；**文档频率**：「差旅」只出现在 1 个 chunk（IDF 高、稀有），「发票」出现在 2 个（IDF 低）；**长度**：3 / 4 / 5，平均 4。
>
> 检索「发票丢了怎么办」→ 分词 `[发票, 丢了, 怎么办]` → 查「发票」精确命中 chunk1 / chunk2，按 `TF × IDF` 打分，**chunk2 分最高、排最前**。

### Q7. 混合检索为什么用 RRF 而不是加权求和？量纲差多少？试过加权吗？RRF的流程是怎么样的？

> 用 RRF 就是因为**两路分数没法直接比**。向量那边给的是 distance（越小越近，量纲是距离），BM25 给的是相关性分（越大越相关，量纲是分数），两者的分布和量纲完全不同。要加权的话得反复调权、还不稳。
>
> RRF 只看**排名**，`score = Σ 1/(k + rank)`，k 固定 60——它对分数绝对值不敏感，所以鲁棒。融合后取 Top 20，再交给 bge-reranker 精排到 Top4，**最终顺序由精排统一纠偏**，混合检索只负责「该进的候选先进来」。
**RRF流程是怎么样的？**
> 第 1 步：两路各自召回并排序，得到各自的排名

向量路（M3E + 向量库）：召回 Top 20，按相似度排出 rank 1~20；
BM25 路：召回 Top 20，按 BM25 分数排出 rank 1~20。
> 第 2 步：对每个 chunk 累加「倒数排名分数」
对出现在任意一路结果里的每个 chunk，套公式：
RRF(chunk) = Σ 1/(k + rank)     # k=60
如果 chunk 只在一路出现，就只加那一项的 1/(60+rank)；
如果 chunk 两路都出现，就把两路的 1/(60+rank) 加起来。
>第 3 步：按 RRF 总分从高到低重排，取 Top 20

>第 4 步：Top 20 交给 bge-reranker 精排，最终取 Top 4

### Rerank 选取的是什么模型，与简单召回有什么区别？算法流程是怎么样的？

**选取的模型？**
>> bge-reranker-base（Cross-Encoder）
**与简单召回有什么区别？**
>>召回（向量）： 把问题「概括成一段摘要」，把每篇文档也「概括成摘要」，然后比这两个摘要像不像。 → 像各自留个印象，再比对印象，快，但细节会丢。
>> Rerank（Cross-Encoder）： 把「问题和文档」并排摆在一起，让模型从头到尾一起读，逐字对照着看「这篇文档到底回没回答这个问题」。 → 像改卷子时，把学生答案和标准答案并排对照着看，慢，但看得细。
**算法流程是什么？**
>> 1. 拼起来：把「问题」和「候选文档」用分隔符拼成一句话，一起拿给模型；
>> 2. 一起读：模型从头读到尾——因为问题和文档连在一起，它读到问题的每个字，都能回头对照文档的每个字；
>> 3. 打一个分：读完，模型给一个 0~1 的「相关分」，代表「这篇文档和问题有多相关」；
>> 4. 排个序：20 篇候选都这样读一遍、各打一分，按分从高到低排，取前 4 名。

### Q9. Rerank 前取 Top20、精排取 Top4，为什么是 20 和 4？调到 50 或 10 会怎样？做过实验吗？

**参考答**：

> 20 是召回池大小，4 是最终喂给 LLM 的上下文数。**取值是召回率和精度、以及延迟之间的平衡**：召回池太小（比如 10），好片段可能压根没进池子，精排再强也没用；太大（比如 50），精排的 Cross-Encoder 要打更多的对，延迟就上去了。
>
> 这两个值都是可配的（`HYBRID_RECALL_K` 等），可以配合评测接口跑对比。

## 第四轮：review_worker（评审）节点校验把关：幻觉检测 + 相关性打分

### review_worker做了什么？怎么做的？

**做了什么：一次 LLM 调用，同时输出五个字段**
review_worker 内部是一次 LLM 调用（trace 里 caller="review_agent"），不是分多步，而是一次性同时输出：

|字段	|含义
|hallucination	|幻觉检测：true / false
relevance_score	相关性打分：0~1
risk	风险等级：low / medium / high
verdict	结论：pass / fail
issues	问题清单
注意它是定性判定、不是数值阈值（hallucination 是布尔、risk 是高中低，不是某个分数卡阈值）。

**怎么做的：拿到这五个字段后做裁决**
1. 幻觉优先：只要 hallucination=true（编造内容、篡改原文关键数字/事实、关键信息缺失），不管相关性多高，都落 risk=high，回 planner 重规划补证据——因为「相关性高只说明问对题，不代表答对题」。

2. 相关性低但无幻觉：说明是检索/规划的问题、不是生成的问题，也回 planner 重规划（换检索词、补 SQL）。

3. verdict 路由（架构图里那条）：

pass / passed_by_human / rejected → 走 finalize（出最终答案）；
fail → 回 planner 重规划补证据，但 review_fail_count 上限 1 次，超了直接 finalize 返回兜底话术（你之前确认过的）。

5. fail-open 兜底：评审 LLM 自己失败时，默认按 medium / pass / 0.8 放行——评审故障不卡死正常回答。

一句话总结
review_worker = 一次 LLM 调用同时输出（幻觉 / 相关性分 / 风险 / verdict / issues）→ 按「幻觉优先」做裁决：幻觉或相关性差就回 planner（限 1 次），过了才放行 finalize；risk=high 就靠「回 planner 重规划补证据（限 1 次）→ 还 fail 就兜底话术」。

### Q6. 评审 fail 为什么只重试 1 次？第 2 次还 fail 怎么办？用户拿到的答案是什么样？

**参考答**：

> 只重试 1 次是**防死循环和防成本失控**。评审 fail 说明素材质量不行，回 planner 补证据一般一次就能改善；如果补了还是不行，再重试大概率也是同样结果，不如止损。所以 `review_fail_count` 上限是 1 次（架构图里写 `< 2`），超了直接 finalize。
>
> 第 2 次还 fail 的话，直接 finalize 返回——返回的是**兜底话术**（不是那个没通过评审的 draft_answer），明确告诉用户「暂时无法可靠地回答」，避免把质量不过关的答案放出去。

💡 **口径**：兜底话术其实是「**宁可不答，也不放一个没把握的答案出去**」——这和整个评审 / 防幻觉的定位是一致的。



### Q12. 你在线上用的是 LLM 定性判定，不是阈值——你怎么证明这个判定本身准？

**参考答**：

> 线上 review 节点确实是 LLM 定性判定，输出 `hallucination: true/false` 加 `risk: low/medium/high`，不是数值阈值。**这里要坦诚：目前没有对评审节点本身做过系统的人工准确率核对。**
>
> 我能说的是：评审 LLM 失败时是 fail-open（默认 medium / pass / 0.8 放行），不会因为评审故障卡死正常回答；另外全链路 trace 都落库了，幻觉率、相关性打分这些指标在评测平台上是能算的。**对评审节点本身的准确率做人工抽样核对，是下一步要补的。**

⚠️ **需你确认**：如果你**做过**评审准确率的抽样，把数字补上；没做过就按上面诚实说。**这题面试官非常爱问**，因为它直接检验「你有没有验证过自己的验证器」。



## 第五轮：工程化 / 评估维度及性能（数字在这，我会算）

### Q15. 缓存只缓存检索结果、不缓存回答——为什么不缓存回答？

**参考答**：

> 因为**检索结果变化慢**（跟着知识库更新走），而**回答是 LLM 生成的**，缓存了会过期、会不一致。缓存检索结果，同一个 query 第二次命中就直接跳过 embedding、向量库和 rerank，进 LLM 生成——省掉的是检索那两笔开销，**回答仍然实时生成，保证新鲜和一致**。

💡 **口径**：「**缓存的是检索结果，不是回答。**」

### Q16. 限流是 60 秒 5 次，阈值怎么定的？正常业务需要连续问 6 次呢？ZSet 高并发会不会成为瓶颈？

**参考答**：

> 阈值是可配的（`RATE_LIMIT_WINDOW / RATE_LIMIT_MAX`），5 次 / 60 秒是给单用户的默认保护值，防止短时间大量请求打爆向量库和 LLM。滑动窗口用 ZSet，score 和 member 都是时间戳——先 `ZREMRANGEBYSCORE` 清窗口外的，再 `ZCARD` 数窗口内的，超了拒绝。比固定窗口好在没有边界突刺。

⚠️ **需你确认**：文档**没有**「正常业务连续问 6 次怎么办」和「ZSet 高并发的 Redis 压力」的答案。诚实说法：阈值可配，可以按用户等级 / 白名单放宽；Redis 本身是单线程，高频 ZSet 操作确实是潜在热点，**当前规模没到瓶颈，量大了会考虑本地令牌桶或分层限流**。

### Q17. 会话 TTL 2 小时滑动续期，用户隔 3 小时回来继续问，会发生什么？

**参考答**：

> TTL 是 2 小时、每次访问滑动续期。用户隔 3 小时回来，**Redis 里的会话已经过期了，读不到就视为新会话重新开始**——他前面的对话上下文确实就丢了。

⚠️ **需你确认**：这是文档隐含的行为（「Redis 读不到会话数据 → 视为新会话重新开始」）。被追问「用户觉得上下文丢了怎么办」时，可以补：如果要长期记忆，得单独做持久化的历史存储，不能用 TTL 的缓存当长期记忆。

## 第六轮：评估与闭环（Agent 岗标配）


### 你是如何评估你的rag agent的，有哪些指标？，效果如何？
我评估 RAG Agent 是分两层的，因为「检索」和「完整回答」是两码事。

第一层，检索层——用主服务内部的检索评测集（100 条，人工构造），只看检索命中：Hit@1 = 90%、Hit@3 = 100%。也就是 Top3 基本不漏、大多数问题一次命中。

第二层，端到端——用评测平台上的黄金集（约 50 条），跑 Ragas 四指标：

faithfulness（忠实度）：答案有没有编造；
answer_relevancy（答案相关性）：有没有答非所问；
context_precision / context_recall（上下文精确率 / 召回率）：检索上来的片段精不精、全不全。
但这里有个关键：Ragas 四指标是为「单轮检索-生成」设计的，直接套在 Agent 上会失真——比如正确拒答、澄清反问会被判低分。所以我做了按 route 分层：四指标只评「知识类」分支，另外给 Agent 加了专属维度：

路由准确率：四分类判得对不对；
库外拒答率 / 硬答数：该拒答的有没有瞎编；
引用标注率：答案有没有带引用（生产合规要求）；
平均 ReAct 步数 / 工具调用数：效率和成本。
效果：检索 Hit@1 90%、Hit@3 100%；引用标注率做到 96.7%；延迟 P50 压到 2 秒以内。整套评测是自动化的——测试集生成 → 批量评测 → BadCase 闭环 → 发版自动回归，上线后能持续迭代。

指标速记表
层	指标	效果
检索层	Hit@1 / Hit@3	90% / 100%（100 条检索评测集）
端到端（四指标）	faithfulness / answer_relevancy / context_precision / context_recall	Ragas 自动打分
Agent 专属（按 route 分层）	路由准确率、拒答率、引用标注率、工具效率	引用标注率 96.7%
性能	P50	< 2s（预热+缓存命中）


### Q18. 检索评测集 100 条、端到端黄金集 50 条，这两套怎么构造的？

> ⚠️ **高频追问点：别把「两套评测集」说混**——检索评测集测 Hit@K，黄金集测端到端四指标，用途不同。

**参考答**：

> 我有**两套评测集，用途不一样**：
>
> **第一套是检索评测集（100 条）**，只测检索层，主服务内部用，看 Hit@K——Hit@1 是 **90%**（90/100）、Hit@3 是 **100%**。人工构造，围绕知识库内容出题。
>
> **第二套是端到端黄金集（约 50 条）**，在评测平台上用，测完整回答质量，打 Ragas 四指标（faithfulness / answer_relevancy / context_precision / context_recall），再加 Agent 的路由准确率、拒答率这些维度。
>
> 两套都按 **5 类题型**分类（fact / reasoning / vague / out_of_kb / edge）：简单事实查询、多段文档综合推理、模糊提问、知识库不存在的问题、易混淆边界。这样能覆盖不同失效模式——事实查询考基础召回，多段推理考多路召回，模糊提问考改写，库外问题考拒答防幻觉，边界题考精排。

### Q20. 从线上发现一个坏 case，到进评测集、到改完验证，整个闭环怎么走？

**参考答（结合 EVAL.md §2.2）**：

> 这个闭环是评测平台的核心价值，走完整链路：
>
> 1. **线上回流**：连接被测服务的生产库，把真实失败样本导入平台（`source=production`，记录库/表/行，可追溯）；按 question 去重，只导入没修复的；
> 2. **人工筛选**：补 ground_truth、剔误报，固化成候选样本；
> 3. **批量评测**：跑黄金集，Ragas 四指标打分，按题型 + 路由双维度识别低分（库外题看拒答信号、模糊题放宽阈值、误路由必标）；
> 4. **人工审核打标签**：幻觉 / 召回差 / 答非所问，写优化记录；
> 5. **修复被测服务**：补文档 / 调检索 / 改 prompt；
> 6. **重跑验证** → 连续通过 + 人工确认；
> 7. **转正**：复制为测试集样本（**不是移动**，保留 badcase 可回溯），按 question 判重防堆积；
> 8. **发版回归**：主服务发版自动跑黄金集，输出新旧指标 delta，坏例不再复发。

💡 **口径**：闭环的亮点是「**复制而非移动**」——转正后 badcase 记录保留可回溯，同时按 question 判重防止反复转正堆积重复样本。这体现的是**数据生命周期设计**，不只是"修了个 bug"。

💡 **加分点**：可以提「线上 badcase 回流」——真实用户问法比合成题更有价值；这比「手工攒测试集」高级一档。

⚠️ **需你确认**：「周期多长」如果没量化过，就说「按提交 / 发版节奏走，没有严格统计周期」。

## 第八轮：补充追问

### Q24. 多轮对话的记忆到底存在哪？Checkpoint 和 Redis 是什么关系？

**参考答**：

> 是**两层，职责分开**的：
> - **LangGraph Checkpoint**（`AsyncSqliteSaver`）存的是**图执行状态**——每个节点的 state，用于断点续跑和人在回路的恢复；
> - **Redis 会话上下文**（`agent:session:{sessionId}`）存的是**跨请求的对话历史**——用户提问、思考、工具结果、回答，TTL 2 小时滑动续期。
>
> 简单说：**Checkpoint 管「图怎么跑到这儿」，Redis 管「这个用户之前聊了什么」。** 前者是执行层的状态，后者是业务层的上下文。

💡 **口径**：「**Checkpoint 管执行状态，Redis 管对话上下文，两者不重叠。**」

## 第十一轮：Redis 会话与多实例架构

### Q35. 会话上下文为什么放 Redis？多实例 / 负载均衡怎么落地？key 和过期时间是什么？

> 这是一串连贯的追问链，从「会话放 Redis」一路追到「多实例」「负载均衡」「具体 key/TTL」。按下面的顺序答。

**参考答**：

> **① 为什么会话上下文放 Redis（核心：无状态）**：多轮对话的历史如果存在某个服务进程的内存里，这个进程就「有状态」了——用户下一句话被负载均衡分到别的实例，那个实例内存里没有这段历史，多轮对话就断了。所以把会话上下文放到 Redis（外部共享存储），服务进程自己什么都不记，就是**无状态**的，多实例随便扩、随便接。
>
> **② 为什么需要多实例**：单实例有硬上限——LLM 线程池 + SQLite 写锁竞争，真实链路建议并发 ≤4。问答链路又重，用户一多就排队。多实例就是横向加机器分摊负载，同时也为了高可用（一个实例挂了不至于全挂）。
>
> **③ 模型服务单实例能支撑吗**：能，但要分清——多实例说的是「应用层」，而 LLM、embedding（Ollama）、reranker 都是**独立服务、各自共享一个**，支撑上面 N 个 app 实例。代价是模型服务各自成了**单点 + 吞吐瓶颈**，尤其 LLM 吞吐（README 里明确说了「真正瓶颈是 LLM 吞吐」）。
>
> **④ 负载均衡怎么做**：自研的服务目录。
>
> **⑤ key 和过期时间（具体细节）**：key 是 `agent:session:{sessionId}`，sessionId 是服务端生成的 UUID、下发给前端、之后前端回传。后端拼 key → `GET` 出来 → JSON 反序列化成消息数组（用户提问/思考/工具结果/回答）→ 读不到就当新会话。**TTL 是 2 小时（7200s）、滑动续期**——每次访问刷新 TTL，活跃用户不掉线，连续 2 小时没动静才自动回收。
>
> **⑥ 效果（这套设计带来什么）**：
> - **可水平扩展**：服务无状态 → 流量涨了直接加实例，不用改代码，这是最核心的收益；
> - **高可用**：多实例容灾，一个实例挂了流量切走，服务不中断；
> - **多轮对话连续**：换实例也能接着聊（会话在 Redis，不在某个实例的内存里）；
> - **资源可控**：TTL 滑动续期，不活跃会话 2 小时自动回收，不长期占 Redis 内存。
>
> 再往上一层看，整个 **Redis 三件套各管一个效果**：缓存管「**快**」（检索 KV 缓存把问答 P50 从 3.7~5.5s 压到 <2s）、会话管「**有状态**」（多轮不断 + 无状态扩展）、限流管「**稳**」（保护 LLM 和向量库不被单用户打爆）。

💡 **口径**：这一串的因果链是「**单实例扛不住 → 加多实例 → 多实例要求状态共享 → 会话放 Redis 无状态 → Nginx 轮询 + SSE 关缓冲**」。背下这条链，被追到哪一环都能接住。

💡 **口径**：sessionId 是放**请求体字段**回传的（不是请求头）。面试官问「sessionId 怎么传」直接答：服务端生成 UUID 下发，前端存起来，后续每次请求放进**请求体**带上；后端拼成 `agent:session:{sessionId}` 去 Redis 读。

### Q36. 面试官问「系统总体效果怎么样」怎么答？

## 第九轮：评测平台（项目二，独立加分项）

### Q26. 介绍一下评测平台这个项目，他的工作流程是什么？



> 这是独立于主服务的一个**评测工程**，解决的是「RAG 答得好不好」这件事——以前靠人肉攒问答、逐条打分，不可量化、不可回归、不可定位。我做的是把整条链路工程化：测试集自动生成 → 批量评测 → 指标报告 → BadCase 闭环 → 发版回归。
>
> 架构上分两块：前端 Vue2 + ElementUI 管测试集、任务、报告、BadCase 审核；后端 FastAPI + Ragas 管语料加载、样本生成、批量评测、回归流水线、分块实验。
>
> 关键点是**两个仓库解耦**：评测平台只管「怎么测」，不依赖被测服务内部实现，只通过**评测契约**（接口 + 数据结构）调用被测方。被测方可以是我的主服务，也可以是任何满足契约的 RAG 服务。

**工作流程（Ragas 贯穿「生成」和「打分」两个环节）**：

> - **第一环节·造测试集**：用 Ragas TestsetGenerator 自动生成候选（simple / reasoning / multi_context），人工筛选、核对 ground_truth、标注题型，固化成黄金集（5 类 × 多文档）——「**Ragas 生成 + 人工把关**」；
> - **第二环节·批量评测**：用 Ragas 四指标自动打分，但**按 route 分层**——四指标只评知识类分支，Agent 的路由 / 拒答 / 引用行为用平台自研的专属维度评——「**借力 Ragas 但不盲信**」；
> - **第三环节·BadCase 闭环 + 回归 + 分块实验**：题型差异化识别低分 → 人工审核打标签 → 修复 → 回归验证 → 转正；分块实验隔离变量调切分参数；发版自动回归——**这些是平台自研的评测体系，不是 Ragas 自带的**。

**Ragas 的定位**：

> Ragas 管「生成」和「打分」的体力活，平台管「体系」——测试集管理、按 route 分层、BadCase 闭环、回归。所以是「**借力 Ragas，但不盲信 Ragas**」，这正是评测平台的辨识度。

💡 **口径**：架构上强调「**工具与系统的边界用契约定义**」；工作流程上，重点讲「**Ragas 是引擎、体系是平台自研的**」，别讲成「用 Ragas 做了个工具」。

### Q27. 测 RAG Agent的评测维度是哪些？为什么不能直接套 Ragas 四指标？


**评测维度清单（速记表）**：

| 类别 | 维度 | 评什么 |
|---|---|---|
| **Ragas 四指标**（知识类分支） | faithfulness | 有没有编造 |
| | answer_relevancy | 有没有答非所问 |
| | context_precision | 检索片段精不精 |
| | context_recall | 检索片段全不全 |
| **Agent 专属**（route 分层） | 路由准确率 | 四分类判得对不对 |
| | 拒答率 / 硬答数 / 误拒数 | 拒答行为对不对 |
| | ReAct 步数 / 工具调用数 | 效率与成本 |
| | 引用标注率 | 带不带引用 |


**参考答**：

> 因为 **Ragas 四指标是为"单轮检索-生成"的经典 RAG 设计的**，隐含假设是"答案由检索上下文生成"。但 Agent 的行为超出这个假设：
>
> - **faithfulness（忠实度）**：假设答案能被检索 context 支撑。但 Agent 的 chitchat / ambiguous 分支**根本不检索**，sql 查出来的结构化数据也不在检索片段里，结果正当回答被判成幻觉；
> - **answer_relevancy**：假设答案正面回答问题。但澄清反问（ambiguous 的正确行为）、拒答（out_of_scope 的正确行为）会被判"不相关"，**做对了反而扣分**；
> - **context_precision**：Agent 多轮检索的 references 是多次的并集，混入无关片段，精确率被稀释；
> - **context_recall**：相对可用，但测不了 Agent 的决策和拒答。
>
> 我的做法是**按 route 分层**：四指标只对 `knowledge` 分支算（真实检索-生成的部分，四指标依然有效）；chitchat / ambiguous / out_of_scope 不打四指标。另外新增 **Agent 专属维度**：路由准确率、库外拒答率/硬答数、平均 ReAct 步数/工具调用数、引用标注率。badcase 判定也同步分层——正当拒答不误杀，误路由必标。


> 记忆口诀：recall 低=没捞到，precision 低=排后面，faithfulness 低=编造，relevancy 低=答非所问。

💡 **口径**：「**先确认指标对这类行为是不是有效的度量，再谈打分。**」——这是贯穿整个评测平台的核心思想。

### Q28. 评测指标都偏低，怎么排查是测试集的问题还是系统的问题？

**参考答**：

> 我不会先改系统，而是**先归因**，分四层：
>
> **第 0 层，先验证测试集是不是合格的尺子**（最便宜，先做）：ground_truth 对照原文、题型分布是否合理（vague 和库外题天然低分，不是系统错）、切分参数是否与生产一致；
>
> **第 1 层，用指标组合定位链路**：context_recall 低 = 检索召回不足（查切分/embedding/入库）；context_precision 低 = 排序差（查 top_k/精排）；faithfulness 低 = 生成幻觉（查 prompt/LLM）；answer_relevancy 低 = 答非所问；
>
> **第 2 层，做决定性实验**：分块实验单独测检索层 Recall@k/MRR（不经过生成）——检索高就是生成层问题；再看 badcase 的 contexts，检索结果里有没有标准答案，**有答案没答对是生成问题，没答案是检索问题**；
>
> **第 3 层，对照组**：一次只动一个变量（切分/embedding/prompt/LLM），指标跟着谁变谁就是根因。

💡 **口径**：记忆口诀「**recall 低=没捞到，precision 低=排后面，faithfulness 低=编造，relevancy 低=答非所问**」。先问尺子歪没歪，再问捞到没，最后问答对没。

### Q29. 库外拒答、模糊提问被自动误标成 BadCase，怎么解决？

**参考答**：

> 现象是：黄金集里 out_of_kb（库外拒答）和 vague（模糊提问）总是落进候选 badcase，即使被测服务答对了。根因是**自动判定是纯分数规则 `avg_score < threshold`，代码不感知题型**，而 Ragas 四指标对拒答、澄清天然给低分——正确拒答命中不了检索片段（context_recall≈0），正确澄清的话术和期望答案不匹配。
>
> 反过来还有个坑：库外题如果被测**硬答**（幻觉），分数反而可能高于拒答，纯分数规则连真问题都会漏。
>
> 我的做法是**按题型差异化判定**：out_of_kb 不看分数、看拒答信号（空回答或含"未找到/无法回答"），正确拒答不标、硬答必标；vague 放宽阈值到 min(全局, 0.35)；fact/reasoning/edge 维持原判。

💡 **口径**：核心思想「**先保证 badcase 入口的语义正确，后面的修复回归闭环才有意义**——否则每天在审核假坏例，真问题反被高分掩盖。」

### Q32. 分块实验怎么隔离变量？

**参考答**：

> 分块实验是**只在检索层做、不经过生成**的对比：固定 embedding 和 top_k，只变切分参数（比如 300/30、500/50、800/80），用同一黄金集测 Recall@k / MRR，还能按文档类型分组看。
>
> 这套能解决「切分参数靠拍脑袋」的问题——因为生成层的 LLM 波动被隔离掉了，测出来的就是纯切分对检索的影响。跑完能导出一份生产切分配置建议（整体最优 + 各类型最优），还能一键用最优参数建端到端评测任务验收。
>
> 调参思路是两步：**分块实验筛参数（快、便宜、灵敏），批量评测验收效果（贵、贴近真实）**——两步都跑，数据说话。

💡 **口径**：「隔离变量」是方法论亮点——比"试了 300 好用"高级得多。

### Q33. 你这个评测平台，和 LangSmith / Langfuse 有什么区别？为什么不直接用？

**参考答**：

> LangSmith、Langfuse 本质是**可观测工具**——记录调用链、trace、token 用量，解决"看得见"的问题。而我这个是**评测体系**——测试集管理、自动打分、BadCase 闭环、回归流水线、分块调参，解决"评得准、能回归"的问题。
>
> 两者是**互补关系**，不是替代。可观测工具告诉你"发生了什么"，评测体系告诉你"答得好不好、该怎么改"。而且我有很强的定制需求——比如按 route 分层评测、题型差异化 badcase 判定、线上 badcase 回流转正，这些是通用观测工具不会做的。

💡 **口径**：别说"它们不好"，说「**它们是观测，我是评测体系，互补**」。这是 EVAL.md 简历避坑里明确写的话术。
